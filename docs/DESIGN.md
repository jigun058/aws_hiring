# CareerLens 구현 설계서 (팀 공유용)

구현 담당이 **어떤 기능을 어떤 로직으로 만들고 있는지** 팀원에게 설명하기 위한 문서다.
규칙을 바꾸고 싶으면 해당 항목의 "조정할 수 있는 것"을 보고 알려 주면 된다.

- 상태: **구현 중** (2026-11-19. 설계는 11/17 팀 회의와 로직팀 명세 P1·P2·P3 반영)
- **제출 마감 11/22**(발표 자료와 시연 영상 링크), 발표 11/25
- 표시: `[확정]` 정해진 것 · `[명세]` 로직팀 명세를 그대로 따르는 것 · `[기본값]` 명세가 없어 구현 담당이 임시로 정한 것(팀원이 바꿀 수 있음) · `[미정]` 아직 못 정한 것

## 1. 한눈에 보기

다시 일을 시작하려는 사람이 자기 경험(이전 직장, 아르바이트, 자격증, 원하면 돌봄·지역 활동)을 파일이나 대화로 넣으면, AI 에이전트가 경험 카드로 정리하고, 맞는 직무와 실제 서울시 채용공고를 찾아 주고, 부족한 역량을 채울 국비 교육과정을 추천한다. 공고마다 필수·우대·업무 역량을 자동으로 분석해 두고, 공고 하나를 붙여 넣으면 즉석에서 분석하는 화면도 있다.

```
[트랙 선택] → ① 경험 수집 → ② 경험 카드 → ③ 직무 추천 → ④ 채용공고 → ⑤ 교육과정 추천
               (파일·대화)    (P3 명세)     (팀원 엔진)   (서울시 공고)  (고용24)
                                                            ↑
                                              ⑥ 공고 역량 자동 분석 (P2 명세)
[재취업 이야기 화면]  ← 중장년 재취업이 왜 필요한지 (팀이 내용 제공)
```

핵심 원칙 `[확정]`: **AI(LLM)는 말을 다루는 일만 하고, 판단·점수·순위는 코드와 식이 정한다.** 같은 입력에는 항상 같은 결과가 나오므로 팀원이 검수할 수 있고, "왜 이 점수인가"를 식으로 설명할 수 있다.

| AI(LLM)가 하는 일 | 코드·식이 하는 일 |
| --- | --- |
| 파일·대화에서 경험 내용과 원문 인용 뽑기 | 인용이 원문에 실제로 있는지 검사 |
| 질문 문장 다듬기, 답변 해석 | 다음에 물을 항목 고르기, 인터뷰 끝내기 |
| 사전 규칙으로 못 잡은 문장의 역량 후보 고르기 | 사전 규칙 매핑, 근거 등급(L0~L3) 판정 |
| 규칙으로 부족한 공고에서 구절 종류와 요구 표현 뽑기 | 공고 구절 나누기·종류 판정, 직무 추천 점수와 순위 |
| 추천 결과를 사람 말로 설명 | 부족 역량 계산, 교육과정 적합도 |

- `[기본값]` 첫 화면의 "처음 일자리를 찾고 있어요"는 "준비 중"으로 표시해 확장 방향만 보여 준다.
- `[확정]` 에이전트는 하나다. 역량 사전(182개), 경험 카드, 교육과정은 나중에 트랙이 늘어도 공통으로 쓴다.

## 3. 공통 기반: 역량 사전과 매핑 `[명세]` P1

- **역량 사전**: 182개(`kw_idx` 0~181). C1·C2·C3·C7·C8(159개)만 점수와 교육 연결에 쓴다. C6(8개)는 낮은 가중치. **C4 태도(10개)는 점수에서 빼고 표시만, C5 신체·근무조건(5개)은 점수에서 빼고 필터로만.**
- **세부 기술**: 94개(PostgreSQL, React 등)가 상위 역량에 붙는다.
- **매핑**: 문장 → 역량 번호. 규칙서의 S0~S7 순서(제외 규칙, 긴 표현 우선, 문맥 규칙). 규칙으로 못 잡은 문장만 LLM이 후보 중에서 고른다(`llm_candidate`, 확인 전에는 점수에 넣지 않음).
- **구현 방식** `[확정]`: 규칙서를 보고 새로 짜지 않고, **로직팀이 검증에 쓴 참조 구현 코드**(`p1_engine.map_sentence`, 11/17 받음)를 쓴다. 사전은 최종판 `P1_competency_dictionary_final.csv`를 쓴다.
- **검증** `[확정]`: 참조 구현은 짧은 시간에 만든 코드라 그대로 믿지 않는다.
  1. 정답 세트 50개와 독립 검증 30개를 **자동 시험**으로 넣어, 코드를 바꿀 때마다 돌린다. 규칙서에 적힌 결과(정답 50/50, 검증 28/30)가 우리 쪽에서도 똑같이 나오는지부터 확인한다.
  2. 시험 밖에서 실제 공고·경험 문장 표본을 돌려 이상한 결과를 모은다.
  3. 틀린 것은 고치기 전에 로직팀에 알린다. 규칙을 바꾸는 판단은 로직팀이 한다.
- LLM 후보를 고를 때 쓸 "비슷한 역량 후보 3~5개"는 새 임베딩 서비스 대신 팀원 엔진에 이미 있는 글자 단위 TF-IDF 유사도로 고른다 `[기본값]`.

## 4. 단계별 기능과 로직

### ① 경험 수집 `[명세]` P3

- **입력** `[확정]`: 파일 업로드(PDF, Word, 텍스트, 자격증·수료증 사진)와 대화. PPT는 PDF로 저장해서 올리도록 안내한다.
- **파일 처리** (P3 F3-1):
  1. 파일마다 따로 처리한다. 하나가 실패해도 나머지는 계속한다.
  2. 실패한 파일은 **어떤 파일이 왜 실패했는지** 화면에 분명히 보여 준다(크기 초과, 지원하지 않는 형식, 내용을 읽지 못함 등).
  3. 주민번호·전화·이메일·주소는 가린다.
  4. AI가 경험을 나누고(카드 1장 = 같은 조직 + 같은 기간 + 같은 목적) 항목마다 원문 인용을 붙인다. **인용이 원문에 없으면 코드가 그 값을 버린다.**
- **인터뷰** (P3 5절):
  - 다음에 물을 항목은 코드가 고른다: 역할 → 목적 → 행동 → 성과의 빈칸 → 모호한 항목 → 근거 등급 올리기 → 성과 수치 → 기간·팀 규모 → 어려움.
  - LLM은 질문 은행의 기본 문장을 카드에 맞게 바꿔 말하고, 예시 선택지 2~3개를 붙인다. LLM이 실패하면 기본 문장을 그대로 쓴다.
  - 종료: 핵심 4항목(역할·목적·행동·성과)이 채워짐 / 질문 8개 / "모름·건너뛰기"가 연속 3회 / 사용자가 그만.
- **원칙** `[확정]`:
  - 경력 공백의 이유, 나이, 결혼·출산·육아, 건강, 가족 상황, 소득, 종교, 정치는 묻지 않는다. 경력 공백은 점수에서 깎지 않는다.
  - 트랙 B의 첫 질문은 일 경험부터 연다. 가족 돌봄·지역 활동은 사용자가 고를 수 있는 선택지로만 보여 준다.
  - 오래된 경력(10년 전 직장)도 그대로 인정한다.

### ② 경험 카드 `[명세]` P3

- **형식**: P3 2.1절 필드를 따른다(활동, 유형, 소속, 기간, 유급 근무 여부, 목적, 역할, 행동, 성과, 도구, 어려움, 역량, 출처, 빠진 정보, 항목 상태, 잠긴 항목 등). 처음 만든 `experience_card_template.json`보다 필드가 많으며, P3가 기준이다.
- **역량 하나에 붙는 두 값** (서로 다른 값이다):
  - 연결 방식: 직접 / 유추 / 전이 등 — 경험 문장과 역량을 어떻게 연결했나
  - 근거 등급: 그 경험이 얼마나 확실한가 — 코드가 판정

    | 등급 | 조건 | 계수 |
    | --- | --- | --- |
    | L3 | 본인 행동 + 성과(또는 유효 자격증) | 1.0 |
    | L2 | 본인 행동만 | 0.75 |
    | L1 | 수강·학습만, 도구 이름만 | 0.5 |
    | L0 | 근거 없음 → 저장하지 않고 인터뷰로 다시 묻는다 | 0 |

- **확인**: AI가 만든 카드를 사용자가 확인하거나 고친 뒤 확정한다. 사용자가 고친 항목은 잠겨서 AI가 다시 덮어쓰지 않는다. 사용자가 확정하면 AI 후보 역량도 점수에 들어간다.
- **저장**: "내 경험 데이터베이스"에 누적된다. 로그인이 없으므로 브라우저 접속 단위로 구분한다.
- **조정할 수 있는 것**: 질문 상한 8개, 카드당 역량 상한 8개(P3 제안값).

### ③ 직무 추천 (트랙 B)

- **엔진** `[확정]`: 팀원이 만든 `recommender.py`를 **코드 수정 없이** 쓴다. 팀원이 엔진을 고쳐서 다시 주면 그대로 갈아 끼울 수 있게 하기 위해서다.
- **점수식** (팀원 README 그대로):

  ```
  100 × (0.30 키워드 일치 + 0.25 의미 유사 + 0.20 업무 행동 연관 + 0.15 성과·경험 수준 + 0.10 자격·우대)
      × 경력직 보정(관리직·경력 위주 0.85~0.92)
      × 근거 신뢰도(공고 30건 미만 직무만 최대 −10%)
  ```

  역량 반영 = 연결 방식(직접 1.0 · 유추 0.7 · 전이 0.45) × 근거 계수. 직무군당 최대 2개, 1위 점수의 72% 미만은 추천하지 않는다. 공고 수는 점수에 넣지 않고 따로 표시한다.
- **시뮬레이션에서 나온 문제의 처리** (엔진 바깥에서 처리) `[확정]`:

  | # | 문제 | 처리 |
  | --- | --- | --- |
  | 5 | 태도 역량(C4)이 점수에 들어감 | 엔진에 넘기는 직무 역량 데이터에서 C4·C5를 걸러 낸다 (엔진의 `out_dir`에 걸러 낸 사본을 넘기면 됨을 확인). **11/19 팀 대화에서 이견이 나와 보류** (`TEAM.md` T20) |
  | 6 | 같은 공고가 두 번 나옴 | 엔진이 돌려준 공고에서 거의 같은 공고, 같은 회사·제목을 하나만 남긴다 |
  | 7 | 경력 없는 사용자에게 경력직 공고가 섞임 | 사용자에게 유급 근무 경력이 없으면 "경력" 공고를 뒤로 보낸다 |
  | 8 | 엔진이 카드의 근거 등급을 쓰지 않음 | 로직팀 시뮬레이션 코드(`07_sim_full.py`)와 같은 방식: 엔진의 역량 추출 결과에서 카드에 있는 역량의 근거 강도를 카드 등급 계수(L3 1.0 · L2 0.75 · L1 0.5)로 바꿔 넣는다. 엔진 파일은 그대로다 |
  | 신규 | 엔진이 "회사에서 5년 동안 ~했다"를 직무 경력이 아니라 "기타 경험"(0.6)으로 봄 (Notion 예시 설명에서 발견) | 경험 카드 유형으로 경험 종류를 정한다 `[기본값]`: 직장·인턴·자영업 → 직무 경력 1.0, 프로젝트 0.85, 아르바이트·지역 활동 0.75, 교육 0.65, 가족 돌봄·자격증 → 엔진 판단 그대로. 엔진 판단보다 높을 때만 바꾼다. 직무 경력이면 엔진의 경력직 감점도 풀린다 |

  6·7·8번과 신규 항목은 11/19 구현함. 5번은 보류(엔진 그대로 C4·C5 포함).

- **경험 규칙 보정** `[확정]` (시뮬레이션 2~4번과 P3 7.3절): 경험 규칙은 두 곳에 있다. 엔진이 쓰는 `knowledge.py`의 `EXPERIENCE_RULES` 목록과, 경험 카드 역량을 붙일 때 쓰는 `careerlens.db`의 `experience_keyword_mapping` 표다(시뮬레이션 코드도 둘을 따로 씀). 엔진 파일과 DB 원본은 고치지 않고, 우리 코드가 읽어 들인 뒤 두 곳에 같은 보정을 적용한다. 바꾼 규칙은 파일 하나에 모아 두어 팀원이 한눈에 볼 수 있게 한다.

  | # | 문제 | 처리 (시뮬레이션·P3 권고 그대로) |
  | --- | --- | --- |

  | 3 | "거래처"만 있어도 영업(직접) | EX036은 판매·제안 행동이 있을 때만 직접 연결 |
  | 4 | 엔진 사전이 입력에 없는 역량을 잡음 (박물류 "전기·전자 지식") | 원인: 동의어 "전기"가 "지게차운전기능사·운전기사" 안에서 걸림. 공고 153건과 운전 직무 프로필도 같은 원인으로 오염. 처리 방법은 지혜님과 정한다 (`docs/reports/경험규칙-보정-1119.md`) |
  | 신규 | 가족 돌봄·학부모회 등 트랙 B 경험이 역량으로 안 잡힘 | P3 7.3절 EXB01~05 추가 (모두 전이 연결 0.45) |

  넣은 뒤 시뮬레이션 인물(박물류·최경리)과 시연 인물로 전후 결과를 비교해 팀에 보여 준다. 11/19 구현함: 바꾼 규칙은 `backend/careerlens/experience_rules.py`, 전후 비교는 `docs/reports/경험규칙-보정-1119.md`. 정규식 세부(EXB01에 어머니·아버지 추가 등)는 `[기본값]`.

- **출력**: 직무 TOP 3과 점수, 점수 구성, 근거 역량. AI가 추천 이유를 문장으로 설명한다(점수는 바꾸지 않는다). 점수는 "합격 확률"이 아니라고 화면에 밝힌다.
- **조정할 수 있는 것**: 점수식 가중치와 규칙. 팀원이 엔진 코드를 고쳐서 넘겨 주면 그대로 반영된다.

### ④ 채용공고 연결

- 추천 직무마다 서울시 공고 6건(③의 6·7번 처리 후). 필터: 지역(구), 근무시간·시간제, 마감일.
- **직무 안 공고 순서** `[명세]` P2 3절: 팀원 엔진 `postings_for`의 겹침 계산에 ⑥의 종류 가중치(필수 2 · 업무 1 · 우대 1)를 더한다. 분석 신뢰도 `low` 공고는 뒤로 보낸다.
- **공고 카드** `[명세]` P2 3절: 필수 / 우대 / 업무 역량을 나눠 보여 주고, 사용자에게 있는 것은 체크, 없는 것은 "부족"으로 표시한다. 태도 요구(C4)는 표시만, 근무 조건은 따로 보여 준다. 법정 필수 자격이 없으면 "자격 취득 후 지원 가능"으로 표시하고 ⑤로 연결한다. `low` 공고는 "공고 정보가 부족해요"를 붙인다.

### ⑤ 교육과정 추천

- **데이터** `[확정]`: 고용24 국비 훈련과정 3,173개 (`courses.json` 11/16판). AWS 교육과정은 넣지 않는다. 다시 전처리한 v2는 Kaggle 연동용이라 쓰지 않는다(11/17 회의).
- **로직** (팀원 전처리 문서 그대로):
  1. 부족 역량 = 직무·공고가 요구하는 역량 − 사용자가 가진 역량
  2. 핵심 역량(C1·C2·C3·C7·C8)만 대상으로 한다.
  3. 부족 역량이 붙은 과정을 연관도 순으로 보여 준다. 훈련비, 일정, 지역, 신청 링크를 함께 표시한다.
- 연결된 과정이 없는 직무는 "교육 없이 바로 지원 가능"으로 안내한다.

### ⑥ 공고 역량 자동 분석 (주제의 "기술역량 자동 분석") `[명세]` P2

- **대상**: 서울시 공고 38,185건(유사 중복 제외). 필수·우대 칸이 둘 다 빈 공고가 74%라 칸만으로는 나눌 수 없다.
- **원칙**: 규칙으로 먼저 전부 처리하고, AI는 규칙으로 부족한 공고에만 쓴다. AI는 구절 종류와 요구 표현만 내고, 역량 번호는 3절 매핑이 붙인다.
- **규칙 처리** (AI 없음, 전체 공고):
  1. 공고 칸마다 짧은 구절로 나눈다.
  2. 구절마다 종류를 정한다. 아래 순서에서 먼저 맞는 것으로 정한다: 근무 조건 → 정책 우대 → 경력 조건 → 우대 → 필수 → 업무. "즉시 출근 가능자"는 조건, "지게차 가능자"는 필수다.
  3. 구절에서 역량과 자격을 찾는다. 자격의 필수·우대는 DB 값을 그대로 쓴다. 같은 역량이 여러 번 나오면 필수 > 업무 > 우대 하나만 남긴다.
  4. 분석 신뢰도를 매긴다: 점수용 역량 3개 이상 + 필수·우대·자격 신호가 있으면 high, 2개 이상이면 medium, 1개 이하면 low.
- **AI 보완**: low 공고 중 본문 80자 이상만. P2 명세는 8,616건으로 셌으나 11/19 규칙 처리 결과는 **3,624건**이다(자격증 칸·제목까지 역량을 찾아서 low가 33.5% → 15.9%로 줄었음). 원문에 없는 인용은 코드가 버린다. 규칙과 AI가 다르면 규칙을 남긴다.
- **진행 순서**:
  1. 규칙 처리로 38,185건 전체 결과를 만든다. **11/19 완료**: `backend/careerlens/posting_analysis.py`, 실행은 `scripts/analyze_postings.py`(약 3분). 신뢰도 high 22,883 · medium 9,234 · low 6,068건.
  2. 공고 카드와 직무 안 공고 순서에 반영한다(④).
  3. 즉석 공고 분석 화면: 공고 하나를 붙여 넣으면 그 자리에서 규칙 + AI 결과가 나온다.
  4. 표본 300건으로 규칙 / Nova Lite / Claude Haiku 4.5를 비교한다 (아래 검수 방법).
  5. AI가 규칙보다 나으면, 실측 비용을 보고하고 승인을 받은 뒤 low 공고에 AI 보완을 돌린다.
- **표본 300건 검수 방법** `[확정]`:
  - 표본은 P2 6절대로 뽑는다(상위 10개 직무 7 : 나머지 3, seed 고정).
  - **필수·우대 분류는 사람이 보지 않는다.** 필수·우대 칸이 원래 나뉘어 있는 공고(약 26%)를 정답지로 쓴다. 칸 표시를 지운 본문을 규칙과 AI에 주고, 나눈 결과를 원래 칸과 코드로 비교해 정확도를 자동으로 잰다.
  - 사람(팀원)은 **역량이 맞는지만** 본다. 규칙과 두 모델의 결과가 서로 다른 구절을 먼저 보고, 셋이 같은 구절은 50개만 확인한다.
  - 정확도 표(규칙만 / 모델 A / 모델 B, 구절 종류 정확도·필수 정밀도·역량 정밀도·원문에 없는 인용 수·건당 비용)는 발표 질문 대비 근거 자료로 쓴다(발표 본문에 먼저 내세우지 않음, `TEAM.md` 6절).
  - 통과 기준(P2): 구절 종류 80%, 필수 정밀도 85%, 역량 정밀도 85%, 원문에 없는 인용 0건. 두 모델 차이가 3%p 이내면 싼 모델. AI가 규칙보다 낫지 않으면 AI 보완은 하지 않는다.
- **조정할 수 있는 것**: 종류 판정 신호 단어, 종류 가중치(필수 2 · 업무 1 · 우대 1), AI 보완 범위.

## 5. 에이전트 구조

- `[확정]` LLM 하나가 도구를 골라 부른다: 역량 매핑, 직무 추천, 공고 검색, 교육과정 검색.
- `[확정]` 화면의 5단계 순서는 고정이다. 인터뷰에서 다음에 물을 항목은 코드가 정하고(P3), 에이전트는 그 질문을 말로 풀고 답을 해석한다. 완전히 자유로운 대화로 두지 않는 이유는 시연 중 엉뚱한 방향으로 가는 것을 막기 위해서다.
- **설명·검색·안내 규칙** `[기본값]` (P6 명세 대신, 11/17 회의 문서에 붙였고 이견 없음):

  | 항목 | 규칙 |
  | --- | --- |
  | 추천 이유 문장 | AI에게는 엔진 결과(점수 구성, 근거 역량, 경험 카드의 원문 인용)만 넘긴다. AI는 2~3문장을 쓰고, 근거가 된 사용자 경험을 하나 이상 언급한다. 넘기지 않은 역량이나 숫자가 문장에 나오면 코드가 걸러 낸다. |
  | 말투 | "~에 지원해 볼 만합니다"처럼 단정하지 않는다. 쉬운 말을 쓰고, P3의 금지 주제는 여기에도 적용한다. |
  | 검색 (RAG) | 벡터 DB는 따로 두지 않는다. "검색"은 엔진·공고·과정 데이터를 코드로 걸러 가져오는 도구 호출이다. AI는 도구가 돌려준 결과만 말하고, 0건이면 0건이라고 말한다. 없는 공고나 과정을 지어내지 않는다. |
  | 상태 안내 | 다음 경우마다 정해 둔 안내 문구와 다음 행동을 보여 준다: 파일을 읽지 못함 / 사전에 없는 경험이라 역량으로 연결하지 못함 / AI 후보 역량이 확인 전이라 점수에 넣지 않음 / 추천 직무 없음 / 공고 0건 / 과정 0건 / AI 응답 오류·시간 초과(다시 시도). |

### 화면 품질 기준 `[확정]`

시연하지만 급조된 데모처럼 보이면 안 된다. 실제 서비스처럼 보이는 기준은 다음 여섯 가지다.

1. 첫 화면(서비스 소개와 시작 선택)이 있다.
2. 기다리는 동안 무엇을 하는 중인지 보여 준다 (예: "공고 3만 8천 건에서 찾는 중").
3. 오류가 나면 사람이 읽을 수 있는 안내가 나온다.
4. 빈 화면에는 다음에 할 일을 안내한다.
5. 새로 고침해도 진행 상태와 경험 카드가 남는다.
6. 노트북과 발표장 화면 크기에서 깨지지 않는다.

- 주 사용자가 40~50대이므로 큰 글자, 쉬운 말, 적은 단계를 기본으로 한다.
- 디자인: 구현 담당이 Claude Design으로 시안을 만들어 온다(참고 웹사이트 캡처와 글꼴 첨부). 화면 코드는 그 시안을 따른다.
- 화면 배치: 첫 화면은 단독 페이지. 작업 화면은 위쪽 머리줄(로고, 5단계 진행 표시, 메뉴) + 왼쪽 본문(약 3분의 2) + 오른쪽 에이전트 대화창(약 3분의 1, 모든 단계에서 유지). 본문과 대화창 사이의 경계는 사용자가 끌어서 조절할 수 있고, 3분의 2 대 3분의 1은 처음 값이다. 재취업 이야기와 공고 분석은 대화창 없는 별도 페이지.
- 시연 도구는 일반 화면에 흩어 놓지 않고 왼쪽 아래 버튼으로 여는 서랍 한 곳에 모은다: 처음부터 다시 시작, 예시 인물 불러오기, 원하는 단계로 이동, 미리 저장한 응답으로 재생(인터넷이나 Bedrock 장애 대비, 재생 중임을 화면에 표시).
- 시안이 오기 전에는 기본 부품 모습으로 구조와 동작을 먼저 만들고, 시안이 오면 입힌다. 시안은 11/19까지 오면 11/20 배포에 반영된다.
