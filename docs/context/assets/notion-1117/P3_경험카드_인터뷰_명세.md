# P3. 경험 카드 · AI 인터뷰 명세 (초안)

> 상태: **초안(2026-11-17)**. 담당자 검토 후 확정한다.
> 기준: 인수인계 문서 F2·F3·F4(설계서 v0.2), 개발자 설계서 ①·②, P1 최종 후보본, careerlens.db `experience_keyword_mapping`.
> 개발자의 `experience_card_template.json` 원본은 아직 받지 못했다. 이 문서의 필드는 개발자 설계서에 적힌 항목 이름(활동·유형·기간·목적·역할·행동·도구·어려움·성과·역량·출처·빠진 정보)을 기준으로 했고, 원본을 받으면 키 이름만 맞춘다(10절).

| 구분 | 내용 | 절 |

| 예시 | 상황 → 입력 → 적용 규칙 → 판단 결과 → 예상 출력 | 9 |

[확정] 원칙(바꾸지 않음)
- AI는 사용자가 말하지 않은 수치·역할·결과를 채우지 않는다.
- 모든 추출 값에는 원문 인용을 붙이고, 인용이 원문에 있는지 코드가 검사한다. 없으면 그 값을 버린다.
- 역량은 공통 역량 사전 182개 안에서만 고른다. 사전에 없는 표현은 버리지 않고 따로 보관한다.
- 경력 공백은 에이전트가 먼저 묻지 않고, 점수에서 깎지 않는다.
- 사용자가 직접 고친 값은 잠긴다. 이후 AI가 다시 분석해도 덮어쓰지 않는다.

## 1. 경험 카드의 단위

- **카드 1장 = 같은 조직 + 같은 기간 + 같은 목적.**
  - 같은 동아리라도 "홍보부 활동"과 "회장 활동"은 기간이나 목적이 다르면 2장이다.
  - 한 회사 인턴 중 프로젝트 2개는 목적이 다르면 2장이다.
- 파일 하나에 경험이 여러 개 있으면 나눠서 카드 초안 여러 장을 만든다. 나눈 결과는 사용자가 확인한다("이 자료에서 경험 3개를 찾았어요. 맞나요?").
- 비슷한 카드 2장이 생기면(조직명 같고 기간이 겹침) **병합을 제안만** 한다. 자동으로 합치지 않는다.

## 2. 경험 카드 형식

### 2.1 필드

| 필드(가칭 키) | 의미 | 필수 | 값 규칙 |
|---|---|---|---|
| `card_id` | 카드 번호 | 시스템 | 생성 시 부여 |
| `track` | A / B | 시스템 | 카드를 만든 시점의 트랙. 트랙을 바꿔도 카드는 유지(K-02) |
| `activity` | 활동명 | **필수** | 사용자 표현 그대로. 예: "교내 데이터 분석 학회 프로젝트" |
| `type` | 유형 | **필수** | 7절 표의 값 중 하나 |
| `organization` | 소속 | 선택 | 회사·학교·단체명. 모르면 null |
| `period` | 기간 | 선택 | `{start:"2025-03", end:"2025-06", months:4, is_estimate:false}`. 대략적인 답이면 `is_estimate:true` |
| `is_paid_work` | 유급 근무 여부 | 선택 | 인턴·직장·아르바이트·자영업=true. 경력 개월 계산(P4)에만 쓴다 |
| `team_size` | 팀 규모 | 선택 | 숫자 또는 "혼자". 모르면 null |
| `purpose` | 목적 | **핵심** | 왜 했는가 / 무엇을 해결하려 했는가 |
| `role` | 역할 | **핵심** | 사용자 본인이 맡은 일. "팀원"처럼 이름만이면 모호(5.2) |
| `actions[]` | 행동 | **핵심** | 한 항목 = 동사 + 대상 + 방법. 예: "SQL로 매출 데이터를 월별로 집계" |
| `results[]` | 성과 | **핵심** | 관찰 가능한 변화 또는 산출물. `{text, type:"정량"/"정성"/"산출물", is_estimate}` |
| `tools[]` | 도구 | 선택 | 사용자가 말한 도구만. P1 세부 기술 층으로 표준화 |
| `challenges` | 어려움·해결 | 선택 | 어려웠던 점과 어떻게 풀었는지 |
| `competencies[]` | 역량 | 시스템+사용자 확인 | 2.2 참고 |
| `sources[]` | 출처 | 시스템 | `{source_id, kind:"file"/"chat"/"certificate", file_name}` |
| `missing_information[]` | 빠진 정보 | 시스템 | 비어 있거나 모호한 슬롯 이름 목록. 인터뷰 대상 |
| `slot_status{}` | 슬롯 상태 | 시스템 | 슬롯별 `filled` / `vague` / `missing` / `unknown_by_user` / `skipped` |
| `locked_fields[]` | 잠긴 필드 | 시스템 | 사용자가 직접 고친 필드 |
| `status` | 카드 상태 | 시스템 | `draft` → `interviewing` → `generated` → `confirmed` (→ `archived`) |
| `completeness` | 완성도 | 시스템 | 핵심 4슬롯 중 `filled` 수 ÷ 4 |

**슬롯 값의 공통 형식.** 모든 슬롯 값은 `{value, quote, source_id, by}`로 저장한다.
- `quote`: 원문(파일 문장 또는 사용자 답변)에서 그대로 가져온 조각이다. 코드가 원문 포함 여부를 검사한다.
- `by`: `ai_extracted` / `user_answer` / `user_edit`.
- 화면에는 `value`만 보이고, "근거 보기"를 누르면 `quote`가 보인다.

### 2.2 역량 항목

```json
{
  "kw_idx": 41,
  "keyword": "SQL",
  "category": "C2",
  "skill": "PostgreSQL",
  "match_type": "direct",
  "evidence_level": "L3",
  "evidence_quote": "PostgreSQL로 3년치 매출 데이터를 월별로 집계했고",
  "result_quote": "보고서 작성 시간을 주 2시간에서 30분으로 줄였다",
  "source_id": "file_01",
  "status": "confirmed",
  "user_confirmed": true,
  "is_transferable": false
}
```

| 필드 | 규칙 |
|---|---|
| `kw_idx`, `keyword`, `category` | P1 사전 값. 사전 밖 번호는 저장하지 않는다 |
| `skill` | P1 세부 기술(있을 때만). 예: PostgreSQL, React Native |
| `match_type` | 연결 방식: `synonym` / `direct` / `derived` / `transferable` / `license_implied` / `llm_choice`. **근거 등급과 다른 축이다** |
| `evidence_level` | 근거 확실성: L0~L3(3절) |
| `evidence_quote` | 필수. 없으면 역량을 만들지 않는다 |
| `result_quote` | 성과 근거가 있을 때만 |
| `status` | P1 규칙서 8절 값. 사용자 카드에서는 4.3의 사용자 확인 규칙을 따른다 |
| `is_transferable` | `match_type=transferable`이면 true. 화면에 "전이 역량"으로 표시 |

## 3. 근거 등급 (L0~L3)

### 3.1 판정표 [계수 확정 11/17, 판정 조건은 제안]

근거 등급은 **역량 하나마다** 매긴다. LLM은 판정 재료(인용과 표시값)만 만들고, **등급은 코드가 아래 표로 정한다.**

| 등급 | 조건(코드로 확인) | 계수 | 팀원 엔진 대응 |
|---|---|---|---|
| **L3 성과 확인** | ① 그 역량에 연결된 **본인 행동** 인용이 있고 ② 같은 카드에 **관찰 가능한 성과**(정량·정성·산출물) 인용이 있음. 또는 ③ 유효 자격증에서 나온 역량(`license_implied`, U-03) | 1.0 | 성과 있음 1.0 |
| **L2 수행 확인** | 본인 행동 인용은 있으나 성과 인용이 없음 | 0.75 | 수행 0.75 |
| **L1 추정** | 아래 중 하나: 수강·학습만("배웠다", "수료", "강의를 들었다"), 사용자가 기술 목록에서 직접 고름, 행동 없이 도구 이름만("SQL 써 봤어요"), 수료증 사진만 있음 | 0.5 | 학습만 0.5 |
| **L0 근거 없음** | 역량 이름만 있음, 또는 팀 성과인데 본인 역할이 불명확 | 0 | — |

- **L0은 역량으로 저장하지 않는다.** `missing_information`에 넣고 인터뷰로 확인한다. 점수에도 넣지 않는다.
- 같은 역량이 카드 여러 장에 있으면 **가장 높은 등급**을 쓴다. 여러 장의 L1을 모아도 L2로 올리지 않는다.
- **수강만으로는 L2 이상이 될 수 없다.** 실습·프로젝트 경험을 말하면 그 문장으로 다시 판정한다.
- **"본인 행동"의 판정:** 주어가 사용자(저는, 제가, 1인칭 생략)이거나 `role`에 포함된 일이어야 한다. "우리 팀이 앱을 만들었다"만 있고 본인 역할이 없으면 기술 역량은 L0이다. 역할 질문(5.3 ①)으로 먼저 확인한다.
- **"관찰 가능한 성과":** 수치, 산출물(배포한 앱, 발표한 보고서, 만든 대시보드), 제3자의 평가(수상, 채택)가 해당한다. "많이 배웠다", "보람 있었다"는 성과가 아니다.

### 3.2 계수를 바꾼 이유 (설계서 v0.2 대비)

- v0.2 제안 계수는 L2 0.8, L1 0.4였다.
- 이 문서는 **팀원 엔진의 근거 강도 값(1.0 / 0.75 / 0.5)과 똑같이** 맞췄다. 그래야 `recommender.py`를 고치지 않고 등급 값을 그대로 넣을 수 있고, 트랙 A와 트랙 B가 같은 계수를 쓴다.
- v0.2의 L3는 "자료에 흔적이 있음"을 조건으로 했는데, 자기소개서나 보고서도 결국 본인이 쓴 글이라 파일 출처만으로 등급을 올리지 않는다. 대신 엔진과 같은 기준인 "성과가 있는가"로 바꿨다.

### 3.3 연결 방식(match_type)과 등급을 분리하는 이유

- 개발자 기본값은 직접 / 유추 / 전이를 근거 등급으로 쓰는 것이다. 그런데 이것은 "경험 문장과 역량을 **어떻게 연결했나**"이고, 근거 등급은 "그 경험이 **얼마나 확실한가**"다.
  - 예: "SNS 계정을 운영해 팔로워를 200명에서 350명으로 늘렸다" → 홍보(119)는 `derived`(유추)이지만 성과가 있으므로 L3다.
  - 예: "SQL 써 봤어요" → SQL(41)은 `direct`(직접)이지만 행동이 없으므로 L1이다.
- 팀원 엔진은 이미 두 값을 곱한다(연결 방식 가중치 1 / 0.7 / 0.45 × 근거 강도). 카드에서 두 값을 따로 넘기면 엔진이 지금처럼 계산한다.
- **전이 역량의 등급 상한을 두지 않는다.** P1 규칙서 9절의 "전이 역량은 L1에서 시작"은 철회한다. 엔진이 연결 방식 가중치 0.45로 이미 낮추기 때문에, 등급까지 L1로 묶으면 같은 이유로 두 번 깎인다.

## 4. 역량 태깅

### 4.1 순서

1. **사전 규칙(코드):** 카드의 `actions`·`results`·`tools`·`role` 문장에 P1 F0-1(국문 별칭·세부 기술·문맥 규칙)과 DB 경험 규칙(direct 29·derived 41·transferable 31)을 돌린다. 일치한 것은 `status=confirmed` 후보다.
2. **LLM 닫힌 선택:** 규칙으로 하나도 안 잡힌 행동 문장만 LLM에 넘긴다. LLM에는 그 문장, 임베딩으로 고른 사전 후보 3~5개(이름 + 한 줄 정의)를 주고 "후보 중 선택 / 해당 없음"만 고르게 한다. 고른 이유와 근거 인용은 필수다. 결과는 `match_type=llm_choice`, `status=llm_candidate`.
3. **근거 등급(코드):** 3.1 표로 판정한다.
4. **사용자 확인:** 카드 확인 화면에서 역량 목록을 보여 주고 사용자가 확인하거나 지운다(4.3).

### 4.2 태깅 규칙

| 규칙 | 내용 |
|---|---|
| 근거 없는 역량 금지 | `evidence_quote`가 없거나 원문에 없으면 그 역량을 버린다 |
| 카드당 상한 | 역량은 카드당 최대 8개. 넘으면 C1·C2·C3·C7·C8 → C6 → C4·C5 순으로 남기고, 같은 분류 안에서는 등급 높은 순 |
| C4·C5 | 저장하고 화면에 보여 주지만 점수에는 쓰지 않는다(K-07). 체력·책임감 같은 전이 역량이 여기에 많다 |
| 자격증 | 자격증 사진·이름은 P1 F0-2로 처리한다. 자격 규칙에 있는 자격만 역량으로 연결(`license_implied`, L3). 소방안전관리자처럼 규칙에 없는 자격은 자격 정보로만 저장 |
| 수료증 | 과정명은 courses.json 과정과 맞으면 그 과정의 키워드를 L1로 연결. 맞는 과정이 없으면 과정명에 F0-1을 돌려 L1로 연결 |
| 사전 밖 표현 | "Celery", "노션" 등은 `unmapped_terms`에 보관. 화면에는 "사전에 없는 기술"로 보여 준다 |
| 희망 직무 | 태깅에는 희망 직무를 쓰지 않는다(희망 직무에 맞춰 역량을 부풀리지 않기 위해). 희망 직무는 질문 우선순위(5.3 ④)에만 쓴다 |

### 4.3 사용자 확인과 LLM 후보 [제안]

- P1 규칙서 8절은 "사람이 검토하지 않은 LLM 후보는 점수에 반영하지 않는다"이다.
- 사용자 카드에서는 **카드 주인인 사용자의 확인을 사람 검토로 본다.**
  - 사용자가 확인 화면에서 그 역량을 지우지 않고 카드를 확정하면 `user_confirmed=true`, `status=reviewed_approved`가 되어 점수에 반영된다.
  - 사용자가 지우면 `reviewed_rejected`가 되고, 같은 카드에서 다시 제안하지 않는다.
  - 확정 전의 `llm_candidate`는 점수에 넣지 않는다.
- 이렇게 하지 않으면 사용자 카드의 LLM 후보를 검토할 사람이 없어서 영원히 점수에 못 들어간다.
- 화면 문구: "AI가 찾은 역량이에요. 맞지 않으면 지워 주세요."

## 5. AI 인터뷰

### 5.1 슬롯

| 구분 | 슬롯 | 채워졌다고 보는 기준 |
|---|---|---|
| 핵심 | 역할 `role` | 본인이 맡은 일이 동사로 드러남("데이터 추출 담당", "주문 접수와 재고 관리") |
| 핵심 | 목적 `purpose` | 왜 했는지, 누구를 위해 무엇을 하려 했는지 |
| 핵심 | 행동 `actions` | 동사 + 대상 + 방법이 있는 항목 1개 이상 |
| 핵심 | 성과 `results` | 관찰 가능한 변화·산출물 1개 이상 |
| 보조 | 도구, 어려움·해결, 기간, 팀 규모 | 있으면 좋음. 인터뷰 종료 조건에는 들어가지 않음 |

### 5.2 "모호함" 판정 (코드 + LLM 표시)

| 슬롯 | 모호 기준 |
|---|---|
| 역할 | 직함·이름만("팀원", "인턴", "부원", "막내") |
| 행동 | 동사가 "했다·참여했다·도왔다·담당했다"뿐이고 대상이나 방법이 없음 |
| 성과 | 느낌·배움만("많이 배웠다", "뿌듯했다") 또는 "잘 됐다"처럼 무엇이 변했는지 없음 |
| 목적 | "과제라서", "시켜서"만 있음 → 모호로 보지 않고 `filled`. 억지로 큰 목적을 끌어내지 않는다 |

### 5.3 다음 질문 고르기 (코드)

아래 순서에서 **처음 해당하는 것 하나**를 고른다. 한 번에 질문 1개, 슬롯 1개.

| 순위 | 대상 | 조건 |
|---|---|---|
| ① | 핵심 빈칸 | 역할 → 목적 → 행동 → 성과 순서로 `missing`인 첫 슬롯 |
| ② | 핵심 모호 | 같은 순서로 `vague`인 첫 슬롯 |
| ③ | 자료와 진술 불일치 | 파일과 답변의 기간·역할·수치가 다름 → 어느 쪽이 맞는지 확인 |
| ④ | 희망 직무 관련 역량의 등급 올리기 | 사용자 희망 직무에서 자주 요구되는 역량(직무별 상위 10개) 중 이 카드에서 L1·L2인 것 → "어떻게 썼는지"(L1→L2) 또는 "결과가 어땠는지"(L2→L3). **카드당 최대 2회** |
| ⑤ | 정성 성과의 수치 | 성과가 정성뿐일 때 1회만. "대략이라도 괜찮아요" |
| ⑥ | 기간·팀 규모 | 비어 있을 때 |
| ⑦ | 어려움·해결 | 선택 질문. 앞에서 질문을 4개 이상 했으면 묻지 않음 |

### 5.4 질문 문장 규칙 (LLM)

- 6절 질문 은행의 기본 질문을 카드 내용에 맞게 **바꿔 말하기만** 한다. 질문 대상(슬롯)을 바꾸지 않는다.
- 예시 선택지 2~3개를 붙인다. 선택지는 그 경험 유형에서 흔한 답이어야 하고, 사용자가 말하지 않은 사실을 단정하지 않는다("~같은 일을 하셨나요?"는 가능, "~를 하셨군요"는 금지).
- 이미 답한 내용을 다시 묻지 않는다.
- 금지 질문: 경력 공백의 이유, 나이, 결혼·출산·육아 여부, 건강, 가족 상황, 소득, 종교, 정치. 사용자가 먼저 말한 경우에도 그 이유를 캐묻지 않는다.
- 한 질문은 2문장 이내, 존댓말.
- LLM 호출이 실패하면 질문 은행 문장을 그대로 쓴다.

### 5.5 답변 해석 (LLM → 코드 검사)

| 답변 | 처리 |
|---|---|
| 내용 있음 | LLM이 `{slot, value, quote}`를 만든다. `quote`는 사용자 답변 안의 조각이어야 하고, 코드가 확인한다. 통과하면 `filled`(모호 기준에 걸리면 `vague`) |
| 한 답변에 여러 슬롯 | 묻지 않은 슬롯도 인용이 있으면 함께 채운다. 다음 질문은 다시 5.3으로 고른다 |
| 모름·기억 안 남 | 같은 슬롯을 **쉬운 형태로 1회만** 다시 묻는다(선택지형). 두 번째도 모르면 `unknown_by_user` |
| 건너뛰기 | 즉시 `skipped`. 다시 묻지 않는다 |
| 추정치("한 30% 정도?") | 저장하고 `is_estimate=true`. 화면에 "대략" 표시. 근거 등급 판정에는 그대로 쓴다 |
| 질문과 무관한 답 | 내용이 다른 경험이면 새 카드 후보로 제안. 아니면 같은 질문을 1회 다시 묻는다 |
| 민감 정보(주민번호, 전화번호, 병력 등) | 저장하지 않는다. 가린 뒤 해석한다 |

### 5.6 종료 조건

아래 중 하나라도 해당하면 그 카드의 인터뷰를 끝내고 카드를 만든다(`generated`).

1. 핵심 4슬롯이 모두 `filled`이고, 5.3 ④ 대상이 없거나 이미 2회 물었다.
2. 이 카드에서 질문을 **8개** 했다 [제안].
3. `unknown_by_user`·`skipped`가 **연속 3회**.
4. 사용자가 "그만" 또는 "다음"을 누름.

- 파일만으로 핵심 4슬롯이 이미 채워졌으면 질문 없이 바로 카드를 만든다. 이때도 사용자 확인은 거친다.
- 빈 슬롯이 남은 채 끝나면 카드에 "추가 확인 필요"로 표시한다. 나중에 사용자가 언제든 이어서 답할 수 있다.

|---|---|---|
| `job` | 정규직 | 경력 단절 이전 직장, 현재 직장 |
| `internship` | 인턴 | (드묾) |
| `part_time` | 아르바이트 | 시간제·단기 근무 |
| `self_employed` | — | 자영업·가게 운영 |
| `project` | 수업·개인 프로젝트, 공모전 | — |
| `education` | 수업, 부트캠프 | 국비 교육, 평생교육 강좌 |
| `community` | 동아리·학회·봉사 | 봉사, 학부모회·아파트 자치회·종교 단체 활동 |
| `family_care` | — | 가족 돌봄(아이, 부모, 환자) |
| `certificate` | 자격증 | 자격증 |

### 7.2 트랙 B 원칙

- **경력 공백을 묻지 않는다.** "언제부터 쉬셨나요", "왜 그만두셨나요"는 금지 질문이다.
- 첫 질문은 "예전에 하셨던 일이나, 최근에 해 보신 활동부터 편하게 말씀해 주세요"처럼 **일 경험부터** 연다.
- 가족 돌봄과 지역 활동은 **사용자가 고를 수 있는 선택지로만** 보여 준다. 화면 문구: "집안의 돌봄이나 지역 활동도 경험이 될 수 있어요. 원하시면 추가해 보세요." 에이전트가 먼저 육아·가사 여부를 묻지 않는다.
- 오래된 경력(10년 전 직장)도 그대로 경험으로 인정한다. 기간이 오래됐다고 등급을 깎지 않는다.
- 자격증은 이름만 받아도 된다(사진은 선택). 이름이 licenses 표와 맞으면 P1 F0-2로 처리한다.

### 7.3 가족 돌봄·지역 활동의 역량 연결 [제안: 신규 경험 규칙]

DB 경험 규칙에는 가족 돌봄·가사·학부모회 규칙이 없다(요양원 봉사 EX019, 아동센터 돌봄 EX034만 있음). 아래 규칙을 추가한다. 과대평가를 막기 위해 **모두 transferable**로 두고, 구체적인 행동이 있을 때만 연결한다.

| 규칙 ID(가칭) | 표현 조건 | 역량 | 연결 방식 | 비고 |
|---|---|---|---|---|
| EXB01 | (부모님·시부모님·어르신·환자) AND (돌보·간병·병원 동행·식사 수발·투약) | 70 돌봄 서비스, 1 노인 돌봄 지식 | transferable | 단순히 "모시고 산다"는 연결 안 함 |
| EXB02 | (아이·자녀) AND (등하원·숙제 지도·학습 지도·놀이) | 71 아동 보육·지도 | transferable | "아이를 키웠다"만으로는 연결 안 함 |
| EXB03 | (학부모회·자치회·반상회·바자회·동호회) AND (총무·회계·임원·회장) | 167 조직 운영, 92 사무 행정 | transferable | 맡은 직책이 있어야 함 |
| EXB04 | (회비·장부·가계부·회계) AND (엑셀·정리·관리) | 36 스프레드시트(엑셀) | transferable | 엑셀을 썼다는 말이 있을 때만 36 |
| EXB05 | (반찬·도시락·급식·단체 식사) AND (만들·준비·조리) AND (봉사·행사·단체·○인분) | 85 조리 | transferable | 가정 요리는 연결 안 함. 단체 조리만 |

- 이 규칙으로 잡힌 역량도 3.1 표대로 등급을 정한다. 예: "2년 동안 어머니 병원 동행과 투약을 챙겼다"는 행동 있음, 성과 없음 → 70 돌봄 서비스 L2, 전이 역량.
- 엔진의 연결 방식 가중치(transferable 0.45)가 적용되므로, 가족 돌봄만으로 요양보호사 직무 점수가 높게 나오지는 않는다. 대신 "관련 경험이 있어요"라는 설명 근거로 쓰인다.
- 요양보호사처럼 법정 필수 자격이 있는 직무는 자격이 없으면 "자격 취득 후 지원 가능"으로 따로 보여 준다(개발자 설계서 ⑤).

## 8. 기능 명세

### F3-1. 파일에서 경험 추출

| 항목 | 내용 |
|---|---|
| 기능 ID | F3-1 |
| 목적 | 업로드 파일 하나에서 경험 후보를 나누고 슬롯 값을 원문 인용과 함께 뽑는다 |
| 입력 | 파일 1개의 텍스트(코드가 추출), 파일 종류, 트랙 |
| 필수 입력 | 텍스트, source_id |
| 선택 입력 | 사용자가 적은 파일 설명 한 줄 |
| 판단 규칙 | ① 코드: 텍스트 추출 → 개인정보 패턴 가리기(주민번호·전화·이메일·주소) ② LLM: 1절 단위로 경험 분리, 슬롯별 `{value, quote}` ③ 코드: 인용 검사, 실패한 값 삭제 ④ 코드: 5.2 모호 판정, `slot_status`·`missing_information` 생성 |
| 조건 분기 | 경험 0개 → "이 자료에서 경험을 찾지 못했어요" + 대화 입력 안내 / 경험 2개 이상 → 분리 확인 / 자격증·수료증 사진 → F0-2 또는 수료증 규칙(4.2)으로 바로 처리 |
| 예외 처리 | 텍스트 추출 실패·빈 파일·지원하지 않는 형식·크기 초과 → 파일 이름과 이유를 보여 주고 나머지 파일은 계속 처리(개발자 설계서 ①) / LLM 형식 오류 → 1회 재요청 → 실패 시 그 파일만 실패 처리 |
| 출력 | 카드 초안 n장(`status=draft`) |
| 다음 단계 | F3-5 태깅, F3-2 질문 고르기 |
| 검증 기준 | 모든 슬롯 값의 인용이 원문에 존재(100%). 원문에 없는 수치가 카드에 0건 |

| 항목 | 내용 |

| 목적 | 지금 카드에서 물어야 할 슬롯 하나를 고른다 |
| 입력 | 카드(`slot_status`, 역량과 등급), 이 카드의 질문 기록, 사용자 희망 직무 |
| 필수 입력 | 카드, 질문 기록 |

| 항목 | 내용 |
|---|---|
| 기능 ID | F3-4 |
| 목적 | 사용자 답변을 슬롯 값으로 바꾼다 |
| 입력 | 질문, target_slot, 사용자 답변, 카드 |

### F3-5. 역량 태깅

| 항목 | 내용 |
|---|---|
| 기능 ID | F3-5 |
| 목적 | 카드의 행동·성과·도구·역할에서 공통 역량을 찾는다 |
| 입력 | 카드 슬롯 값과 인용 |
| 필수 입력 | actions 또는 tools 또는 role 중 하나 |
| 선택 입력 | 자격증·수료증 정보 |

| 조건 분기 | 규칙 일치 → confirmed 후보 / 규칙 0개인 행동 문장 → LLM 닫힌 선택 → llm_candidate / 해당 없음 → unmapped_terms |
| 예외 처리 | 인용 없는 역량 → 버림 / 카드당 8개 초과 → 4.2 순서로 자름 |

| 다음 단계 | F3-6 |

### F3-6. 근거 등급 판정

| 항목 | 내용 |
|---|---|
| 기능 ID | F3-6 |
| 목적 | 역량마다 L0~L3를 정한다 |
| 입력 | 역량 항목, 그 역량에 연결된 행동 인용, 카드의 성과 인용, 학습 표현 여부, 출처 종류 |
| 필수 입력 | 역량 항목 |
| 선택 입력 | 자격 정보 |
| 판단 규칙 | 3.1 표. 학습 표현 목록: 배웠·수강·수료·강의를 들·공부했·익혔 |

### F3-7. 카드 생성·확인·확정

| 항목 | 내용 |
|---|---|
| 기능 ID | F3-7 |
| 목적 | 카드 문장을 정리해 사용자에게 보여 주고 확정한다 |
| 입력 | 슬롯 값, 역량과 등급 |
| 필수 입력 | activity, type |
| 선택 입력 | 없음 |
| 판단 규칙 | LLM은 슬롯 값을 짧은 문장으로 다듬기만 한다(새 사실 추가 금지, 다듬은 문장도 인용 검사). 화면: 슬롯별 값, 역량 목록(등급·전이 표시), 추가 확인 필요 |

| 검증 기준 | 확정 전 llm_candidate가 점수 입력에 0건 |

## 9. 예시 (상황 → 입력 → 적용 규칙 → 판단 결과 → 예상 출력)

**예시 1. 도구 이름만 말함**
- 상황: 트랙 A 사용자가 대화로 경험을 입력
- 입력: "학교 수업 프로젝트에서 SQL 써 봤어요."
- 적용 규칙: F3-5 사전 규칙(EX006 SQL → 41 direct) / F3-6 행동 없음 → L1 / F3-2 ① 역할 빈칸
- 판단 결과: SQL 역량 후보는 있지만 무엇을 했는지 없음
- 예상 출력: 41 SQL L1. 다음 질문 "이 프로젝트에서 직접 맡으신 일은 무엇이었나요? (예: 데이터 정리 / 분석 / 발표 자료 제작)"

**예시 2. 같은 경험, 답변 후 등급 상승**
- 상황: 예시 1의 이어지는 대화
- 입력: "제가 공공데이터를 SQL로 지역별로 묶어서 표로 만들었고, 그걸로 발표해서 A+ 받았어요."
- 적용 규칙: F3-4 한 답변에 여러 슬롯(역할·행동·성과) / F3-5 EX006 41, EX027 156 발표 derived / F3-6 행동 + 성과(제3자 평가) → L3
- 판단 결과: 핵심 슬롯 역할·행동·성과 채워짐. 목적만 빈칸
- 예상 출력: 41 SQL L3, 156 발표 L3(C6). 다음 질문 "이 분석은 무엇을 알아보려고 하신 건가요?"

**예시 3. 팀 성과, 본인 역할 불명확**
- 상황: 파일(공모전 보고서)에서 추출
- 입력: 보고서 문장 "우리 팀은 React Native로 반려동물 산책 앱을 만들어 최우수상을 받았다."
- 적용 규칙: F3-5 세부 기술 React Native → 179 / F3-6 주어가 팀이고 role 없음 → L0
- 판단 결과: 기술 역량을 본인 것으로 인정할 근거가 없음
- 예상 출력: 179는 저장하지 않음. `missing_information=["role", "179 모바일 앱 개발 근거"]`. 질문 "팀이 함께 한 일 중에서 직접 하신 부분은 어디까지였나요? (예: 화면 개발 / 서버 연결 / 기획·디자인)"

**예시 4. 수강만 함**
- 상황: 수료증 사진 업로드
- 입력: "Python 데이터 분석 실무 과정 수료증"
- 적용 규칙: 4.2 수료증 규칙 → 과정명 F0-1(Python 40, 데이터 분석 115) / F3-6 수강만 → L1
- 판단 결과: 배운 사실만 확인됨
- 예상 출력: 40 Python L1, 115 데이터 분석 L1. 등급 올리기 질문 "과정에서 배운 Python으로 직접 만들어 본 것이 있나요?"

**예시 5. 성과가 느낌뿐**
- 상황: 트랙 A 동아리 경험
- 입력: 성과 답변 "많이 배웠고 보람 있었어요."
- 적용 규칙: 5.2 성과 모호 → `vague` / 5.3 ② / 쉬운 재질문
- 판단 결과: 성과 슬롯 미충족
- 예상 출력: 질문 "완성해서 남은 결과물이 있나요? (예: 행사 개최 / 홍보물 / 참여 인원)". 다시 모른다고 하면 `unknown_by_user`로 두고 다음 슬롯으로

**예시 6. 트랙 B, 이전 직장 경력**
- 상황: 트랙 B 사용자, 첫 질문에 답함
- 입력: "15년 전에 마트에서 3년 동안 계산이랑 재고 관리 했어요. 발주도 제가 넣었어요."
- 적용 규칙: 7.2(오래된 경력도 인정) / F3-5 DB 경험 규칙 EX011(계산 → 77 주문·결제 direct, 53 POS 활용 derived), EX012(재고·발주 → 81 재고 관리 direct, 165 물품·자산 관리·136 꼼꼼함 transferable), EX014(마트 → 78 판매·80 상품 진열·매장 관리 derived) / F3-6 행동 있음, 성과 없음 → L2 / `is_paid_work=true`, months 36
- 판단 결과: 역할·행동 채워짐. 목적은 유급 근무라 `filled`로 봄(5.2). 성과 빈칸. 78·80은 "마트"라는 장소에서 유추한 것이라 사용자 확인 화면에서 지울 수 있게 보여 줌
- 예상 출력: 77·81 L2(direct), 53·78·80 L2(derived), 165 L2(전이), 136 꼼꼼함(C4, 표시만). 다음 질문 "일하시면서 나아진 점이나 맡게 된 일이 있었나요? (예: 재고 실수가 줄었다 / 새 직원 교육을 맡았다)". 경력 공백 질문은 하지 않음

**예시 7. 트랙 B, 가족 돌봄을 직접 추가**
- 상황: 사용자가 "돌봄 경험 추가"를 고름
- 입력: "시어머니가 편찮으셔서 2년 동안 병원 같이 다니고 약 챙겨 드렸어요."
- 적용 규칙: 7.3 EXB01 → 70 돌봄 서비스, 1 노인 돌봄 지식 transferable / F3-6 행동 있음, 성과 없음 → L2 / 5.4 금지 질문(건강·가족 상황 캐묻기 금지)
- 판단 결과: 전이 역량 2개
- 예상 출력: 70 L2(전이), 1 L2(전이). 다음 질문은 성과가 아니라 보조 슬롯 위주로("이때 해 본 일 중 지금 일에 도움이 될 것 같은 게 있으세요?"). 병세나 가족 상황은 묻지 않음

**예시 8. 자격증 이름만 입력**
- 상황: 트랙 B 자격증 입력
- 입력: "소방안전관리자 2급 있어요."
- 적용 규칙: P1 F0-2(자격 규칙에 없음 → 역량 연결 안 함, 담당자 결정)
- 판단 결과: 자격 정보만 저장
- 예상 출력: `license={name:"소방안전관리자 2급"}`, 역량 없음. 공고의 자격 요건 매칭(P4·엔진)에만 쓰임
