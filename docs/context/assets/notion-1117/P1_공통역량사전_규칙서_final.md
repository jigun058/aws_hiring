## 4. 세부 기술 관계와 판단 기준

| 관계 | 기준 | 예 | P4 계수(제안) |
|---|---|---|---|
| 동일 | 같은 대상의 다른 표기·약어·한영 | Postgres=PostgreSQL, 파이썬=Python | 1.0 |
| 하위→상위 | 세부 기술이 상위 역량의 한 종류 | PostgreSQL→SQL(41), AWS Lambda→클라우드(46) | 0.9 |
| 대체재 | 같은 상위 아래 같은 `대체재_그룹` | MySQL↔MariaDB↔PostgreSQL(rdbms), AWS↔GCP↔Azure | 0.6 |
| 상위→하위 | 일반 역량으로 특정 기술 요구에 대응 | SQL 경험→PostgreSQL 요구 | 0.5 |
| 관련 | `관련_기술` 칸에 적힌 짝 | Docker↔Kubernetes, Git↔GitHub, JavaScript↔TypeScript | 0.3 |
| 독립 | 공통 역량에 연결하지 않는 세부 기술 | Git, GitHub | 세부 기술끼리만 비교 |

### 4.1 이번에 바로잡은 과도한 동일시 [담당자 지시 반영]

| 대상 | 이전 | 최종 |
|---|---|---|
| MySQL·MariaDB | 같은 행의 별칭(동일) | **별도 세부 기술**, 둘 다 41의 하위, 같은 rdbms 그룹 → 서로 대체재(0.6) |
| Git·GitHub | GitHub가 Git의 별칭, Git은 15 하위 | **둘 다 독립 세부 기술**. GitHub는 저장소 호스팅 서비스라 Git과 동일하지 않고 관련(0.3). 15 프로그래밍 지식에는 연결하지 않음 |
| React·React Native | React Native 문장에서 React(44)도 잡힘 | **긴 표현 우선 매칭**: React Native를 먼저 찾고 그 부분을 가린 뒤 React를 찾음. 별칭에도 `react(?!\s?native)` 조건 |
| AWS 서비스명 | S3·Lambda·EC2가 AWS 별칭 | **별도 세부 기술 + 문맥 조건**. "AWS Lambda", "Amazon S3", "S3 bucket", "EC2 instance"처럼 쓰였거나 같은 문장에 AWS/Amazon이 있을 때만 46으로 인정. 단독 lambda(람다식)·S3는 미인정 |
| cloud | 단독 별칭 | cloud platforms/services/infrastructure/computing/providers/native 등과 결합할 때만 46 |

### 4.2 긴 표현 우선 매칭 규칙

1. 세부 기술 목록을 **별칭 문자열이 긴 것부터** 대조한다(React Native → React, PostgreSQL → SQL, AWS Lambda → AWS).
2. 일치한 부분은 이후 대조에서 가린다(같은 글자를 두 번 쓰지 않음).
3. 그다음 공통 역량 별칭을 가려진 문장에 대조한다.
4. 예: "React/React Native" → React Native(179), React(44) 각각 1번. "MySQL/MariaDB" → MySQL, MariaDB 각각 기록, 공통 역량은 41 한 번.

## 6. 복지·회사 소개 제외 규칙 (수정본)

**문제(실측).** 이전 규칙은 미국 공고 80,320문장 중 6,845문장을 제외했는데, 그중 요구 신호(experience with, required, a plus 등)와 역량 표현이 함께 있는 문장이 **793개**, 놓친 역량 언급이 **1,480개**였다. 원인은 세 가지였다.
- "We are looking for … experience with Node.js"가 `^we are` 패턴으로 지워짐
- "ML experience is a plus"가 `X is a …` 패턴으로 지워짐
- "computer vision"이 복지 단어 `vision`으로 지워짐

**최종 규칙.**

| 규칙 | 내용 |
|---|---|
| 보호 신호 | 요구 신호(experience with/in, proficient, familiar with, knowledge of, required, preferred, a plus, must have, nice to have, skills in, background in, ability to, years of, you have, qualifications, looking for, seeking, hiring) 또는 보호 표현(tech stack, our stack, we use, you'll/you will, role, looking to hire, engineers, developers, designers, analysts)이 있으면 **문장 전체를 제외하지 않는다** |
| 복지 문장 | 보호 신호가 없고, 머리말(benefits include/package, what we offer, perks, what's in it for you, compensation & benefits)이 있거나 복지 항목(401k, medical·dental, dental·vision, health/life/disability insurance, PTO, stipend, parental leave, learning·equipment budget 등)이 **2개 이상**이면 제외 |
| 복지 항목 가리기 | 보호 신호가 있는 문장에서는 복지 항목 부분만 가린다 |
| 회사 소개 문장 | 보호 신호가 없고, About us로 시작, founded in, used by, backed by, has raised, our customers/clients/mission/investors, we help/build/power/partner with, we're a … company/startup/team/platform, X is a … company/startup/platform 중 하나면 제외 |
| 국문 | `복리후생`·`복지:`·`혜택:` 이후 구간 제외, `4대보험 가입·적용·완비`는 10(인사·노무 지식)으로 보지 않음 |

## 8. 매칭 상태와 점수 반영 규칙 [담당자 지시 반영]

| status | 만들어지는 경우 | 기본 매칭 점수 | 화면 |
|---|---|---|---|
| `confirmed` | 사전 별칭·세부 기술·문맥 규칙·자격 규칙으로 일치 | **반영** | 일반 표시 |
| `rule_f04` | F0-4로 175 판정 | 반영. 단 P2가 그 문장을 요구(required/preferred/responsibility)로 분류했을 때만 | 일반 표시 |
| `license_implied` | 자격에서 추정 | P4에서 정함(경험 근거와 구분 저장) | "자격 기반" 표시 |
| `llm_candidate` | F0-3에서 LLM이 후보 중 선택, **사람 검토 전** | **반영하지 않음** | "확인 중인 역량" |
| `reviewed_approved` | 사람이 llm_candidate를 승인 | 반영(이후 같은 표현은 사전 별칭으로 추가해 confirmed로 처리) | 일반 표시 |
| `reviewed_rejected` | 사람이 기각 | 반영 안 함, 같은 문장·표현으로 다시 제안하지 않음 | 표시 안 함 |

`llm_candidate` 상태를 점수에서 어떻게 다루는지는 공고 쪽과 사용자 쪽이 다르다.

- **공고 쪽 요구역량이 llm_candidate일 때:** 필수·우대 충족률의 **분자와 분모 모두에서 뺀다**. 확인되지 않은 요구 때문에 사용자 점수가 깎이지 않게 하기 위해서다. 공고 카드에는 "확인 중인 요구사항"으로 보여준다. 공고 요구역량의 절반 이상이 llm_candidate면 P2 분석 신뢰도를 low로 내린다.
- **사용자 쪽 역량이 llm_candidate일 때:** 그 역량으로 공고 요구를 충족했다고 보지 않는다. 다만 "부족 역량"으로 분류하지도 않고 "검토 대기"로 표시한다. 검토 후 승인되면 점수를 다시 계산한다.
- **"검토 후 예상 점수":** llm_candidate가 모두 승인됐다고 가정한 점수를 따로 계산해 보여줄 수 있다. 이 값은 실제 경험 일치도가 아니다.
- **검토 기록:** 검토자, 일시, 결정, 사유를 남긴다. 승인된 표현은 사전 별칭 추가 후보 목록에 올린다.

## 9. 경험 표현 연결 (P3로 넘기는 규칙)

- careerlens.db `experience_keyword_mapping` 1,231개 중 synonym 1,130개는 국문 별칭으로, direct 29·derived 41·transferable 31개는 경험 규칙으로 쓴다.
